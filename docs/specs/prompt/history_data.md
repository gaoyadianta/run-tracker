# Prompt 历史数据增强（分层降采样）

## 1. 背景与目标

当前 AI 提示词主要基于“当前瞬时状态”（距离、速度、时长、步数、步频），缺少可供模型进行趋势判断的历史序列信息。
目标是在不显著增加 token 成本和延迟的前提下，把“可控规模”的历史数据附加到 prompt 中，让模型可以进行趋势分析（例如配速稳定性、步频变化、后程衰减）。

## 2. 需求

1. 历史数据必须做降采样，且按“离当前时间越远，采样越稀疏”的策略处理。
2. 最近 5 分钟保留全量数据；5-10 分钟每 10s 采样；10-20 分钟每 30s 采样；继续向远端递增采样间隔。
3. 历史数据字段至少覆盖：
- 配速/速度趋势
- 距离趋势
- 位置趋势
- 步频趋势
- 步数趋势
4. 必须控制总体数据量，避免 prompt 无限膨胀。
5. 常规播报与跑步总结都应使用增强后的历史上下文。

## 3. 采样策略（最终）

按“相对当前时刻的 age”分层：

- `0 ~ 5 min`：全量（不额外稀疏）
- `5 ~ 10 min`：`10s` 一点
- `10 ~ 20 min`：`30s` 一点
- `20 ~ 40 min`：`60s` 一点
- `40 min+`：`120s` 一点

补充规则：

1. 无论如何保留首点和末点。
2. 若分层采样后点数仍过多，启用二次压缩（优先保留最近数据，稀释更早数据）。
3. 设置最大点数预算（实现中默认 `180` 点）。

## 4. 数据结构与字段

每个样本点包含：

- `tSec`: 跑步开始后的相对秒数
- `distM`: 累计距离（米）
- `speedKmh`: 当前段速度（km/h）
- `lat`,`lon`: 位置（经纬度，保留有限小数）
- `cadSpm`: 步频（spm，可为空）
- `steps`: 累计步数（可为空）

其中：

- 位置、距离、速度来自轨迹点序列；
- 步频、步数来自步态采样序列并按时间对齐（取“该时刻之前最近值”）。

## 5. 接入设计

1. 新增 `RunningTrendHistoryBuilder` 负责构建历史趋势数据。
2. `TrackingManager` 增加总步数序列（与现有步频/步长序列同节奏采样）。
3. `RunningContext` 新增 `trendHistory` 字段。
4. `RunningContext.toAIContext()` 在原有“当前状态”文本后追加“历史趋势采样”段。
5. `CurrentRunViewModel` 在构建 `RunningContext`（常规播报、总结播报）时注入 `trendHistory`。

## 6. 体量评估与约束

估算（1 小时跑步）：

- 1~3s 定位频率下，原始轨迹约 1200~3600 点；
- 分层采样 + 最大点数预算后，控制在约 180 点以内；
- 以紧凑 tuple 文本格式编码，可将历史段控制在可接受范围。

风险与控制：

1. **风险**：历史点过多导致 token 增长。
2. **控制**：分层采样 + `maxPoints` 限制 + 二次压缩。
3. **风险**：数据时间戳缺失/不稳定。
4. **控制**：时间轴回退到“基于总时长与点数的估算偏移”。

## 7. 非目标

1. 不在本需求中实现“全量轨迹上传”或“外部存储检索”。
2. 不在本需求中引入复杂统计模型（如卡尔曼滤波、聚类）。
3. 不修改 ASR/LLM/TTS 协议，仅增强 prompt 内容。
